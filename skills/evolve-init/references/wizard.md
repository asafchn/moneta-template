# Init conversation

Run this wizard in the agent chat, one unanswered question at a time. Reuse choices already provided in the invocation or current setup; never ask the user to re-enter them. Suggest defaults, but wait for an actual answer when a choice is required. Do useful read-only preparation between questions. Preserve answers and the exact destination across retries.

1. **Provider.** Ask "GitHub with gh, or GitLab with glab?" For GitLab, obtain the host (gitlab.com or their self-hosted instance). An explicit existing-repository URL can supply the provider/host; if it conflicts with a stated preference, resolve the mismatch rather than silently switching.
2. **Authentication.** Verify the selected CLI is installed and authenticated to that host: `gh auth status` for GitHub, or `glab auth status --hostname <host>` for GitLab. Identify the active account without printing tokens. A failed network/sandbox request is not proof of bad credentials. If login is required, ask the user to complete `gh auth login` or `glab auth login --hostname <host>` in their terminal, then verify and resume. Authentication secrets never go in chat, nodes or connection files. Only the selected provider's CLI is required; Git access to the private Moneta bootstrap is a separate prerequisite.
3. **Destination.** Ask "Create a new repository, or use an existing one?" For existing, ask for its URL, verify it matches the provider/host, and preserve its current owner and visibility. Skip the new-repository ownership/name/visibility questions.
4. **New repository owner.** Ask "Your personal account, or an organization/group?" GitHub uses an account or organization; GitLab uses a personal namespace or group/subgroup. For personal, resolve the authenticated account's namespace. For an organization/group, collect the exact existing owner or namespace path and inspect accessible metadata/creation permissions. This choice does not authorize creating an organization or group.
5. **New repository name and visibility.** Ask for the repository name, then visibility: private (recommended), or an explicitly chosen provider-supported alternative. Keep these separate from ownership: an organization repository can be private. For restricted organization/group policies, report the concrete constraint and ask for a compatible choice; do not silently change visibility or owner.
6. **Memory area and role.** Apply the invocation's optional agent-slug; omission selects general without another scope question. Ask for the actual role file only if enrolling a role and its path is unknown. General without a role is valid. Retain source intent if evolve entered this wizard as a setup prerequisite.
7. **Complete the selection.** Briefly state provider/host, account or namespace, repository name or existing URL, visibility for new repositories, selected memory area and optional role. Prepare the exact bootstrap/enrollment changes. Continue when these values are supplied and creation/reuse is authorized; do not add a redundant confirmation after explicit choices. Unresolved destination or visibility choices remain pending.

Return these answers to evolve-init's provider branch. Creation must use explicit destination and visibility arguments; provider defaults are not the user's selection. If remote creation already succeeded, retain its URL and resume rather than creating another repository.

Authentication reference: [GitLab status](https://docs.gitlab.com/cli/auth/status/) and [GitLab login](https://docs.gitlab.com/cli/auth/login/). Inspect the installed CLI help for available flags.

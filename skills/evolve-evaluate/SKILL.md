---
name: evolve-evaluate
description: Review guidance changes with tool evidence and attributed judgments, or look up prior assessments for message deduplication.
---

Apply [memory selection](../knowledge-search/references/memory-scope.md), retaining an explicit parent selection or defaulting a direct call without agent-slug to general. Resolve [the runtime connection](../knowledge-search/references/connection.md); access `evaluation-root/<memory-scope>/<agent>/` directly. During init before connection, accept those explicit paths and identities from the parent. Use agent: unassigned if no actor is enrolled; the evaluator worker name never selects another area. Evaluation files are not ordinary graph-search nodes. Use the existing host's tools; this skill supplies the review procedure, not a custom runner.

For `mode: lookup`, follow [assessment lookup](references/message-lookup.md) and return its result; the review sequence below does not run. Otherwise use the review sequence.

1. **Fix the subject.** Record the baseline Git revision, candidate branch/revision or exact diff, original request, relevant role-file revisions, source evidence and intended improvement. Record `source-mode` and its evidence boundary in the Markdown body. Treat any later candidate change as a new assessment subject.
2. **Read the criterion.** Use existing active criteria and the task's original acceptance conditions. Record criterion revision. If no criterion exists, derive a proposed rubric from the original request and applicable standards, label it draft, and keep any numeric proposal score uncalibrated. Never rewrite criteria in response to a failing candidate. Without an explicit scale, leave scores empty and provide the qualitative findings.
3. **Check deterministic properties with existing tools.** Validate node frontmatter against the local JSON Schemas using an available validator; follow [offline validation](references/offline-validation.md) for local registry setup and reliable record serialization. Check edge target existence, allowed endpoints, inverse symmetry, unique slugs and exact node/agent index descriptions and area-local relation targets. Use Git diff/status to verify changed-file scope, and graph checks to verify every relation stays in the selected area. Verify read isolation from actual retrieval/tool-access evidence; Git cannot prove which files were read. If access evidence is incomplete, record read isolation as unverified. An agent-specific candidate cannot modify shared native plugin instructions without a separate user-scoped request. For a coding correction, use the project's applicable tests, compiler, type checker or linter; for calculations, use a calculator or symbolic checker. Read actual output and exit status. Record command, working directory, subject revision and evidence location. Unavailable or unrun checks remain so.
4. **Review task fulfillment.** Compare the deliverable with the original request, relevant agent responsibilities, API documentation and standards. Separate executed checks from agent/human judgments. A passing test may miss the actual requirement. Verify that each alleged defect exists and that the recommendation follows from its evidence. Read [the metric guidance](references/metrics.md) when choosing or interpreting measures.
5. **Compare outcomes when evidence permits.** For a claimed performance improvement, compare baseline and candidate on the same tasks with the same tools, criteria and effort allowance. Include other relevant cases where available; do not equate reproducing the source correction with generalization. Record every attempt and the selected final outcome. A graph diff alone cannot establish task-performance gain. Additional paid experiments need an agreed budget.
6. **Save the review.** Write a Markdown record under `evaluation-root/<memory-scope>/<agent>/results/` using [the result template](../init/assets/templates/evaluation-result.md) and the linked JSON Schema. Record executed checks, metrics with sources, scored judgments, findings, recommendation and limitations. Missing observations stay null/unknown. Keep transcripts and sensitive artifacts in private local evidence; share reviewed summaries/references in the MR.
7. Return the result path and supported findings to the parent. Request corrections for material defects; rerun affected checks after changes. The parent can open an MR with explicitly limited evidence, but must not describe a proposal assessment as demonstrated agent improvement.

The lectures teach method-specific verification and evaluation. This skill adapts those distinctions to Markdown knowledge changes; it does not implement their trained reward models or prescribe a universal memory-admission threshold.

---
name: extend
description: Guide a wizard to decide whether knowledge needs an existing node, a new node type or an edge type, then propose the necessary graph schema changes through review.
---

Before substantive work, apply [local clone freshness](../knowledge-search/references/freshness.md) using the originating runtime and machine-local config. A parent supplies the same checked connection to children; refresh again if an hour passes. Initial offline preparation before a repository exists records sync as pending and does not claim retrieved knowledge.


Retain and pass the originating runtime root, profile path, resolved connection and explicit agent-slug to every nested skill or child. Resolve bundled roles/skills from that exact root; never locate a same-named skill in another installed instance.

1. **Select context.** Apply [memory selection](../knowledge-search/references/memory-scope.md) and verify [reviewed state](../knowledge-search/references/reviewed-state.md). Use the active connection and selected area's catalogs. Missing setup reaches init while retaining the request; supplied agent-slug passes through explicitly. Completion: one repository, reviewed revision and memory area are fixed.
2. **Understand the need.** Ask one unanswered question at a time: what knowledge or relationship is missing, with a concrete example and the retrieval question it should answer? Reuse visible context. Read the node/edge catalogs and schema-definition index; use knowledge-search for relevant existing nodes. Completion: a concrete need and nearest existing representation are known.
3. **Choose the representation.** Explain the smallest suitable option: add a node of an existing type, add an existing relation, extend a type's fields, create a node type, create an edge type, or make no change. A node type needs distinct semantics and structured data reused across instances; one unusual fact alone need not become a type. A relation describes a connection; raw telemetry and evaluation records keep their separate storage. Raise overlap, migration and scope changes to the user. Completion: the user chooses the representation, or their explicit request already settles it with no discovered material conflict.
4. **Define it together.** For a node type, collect its name, description/discovery cues, directory, data fields with required/optional rules, one valid example and one invalid example. For connections, recommend relevant existing types/nodes and explain why; an isolated node is valid. For a new edge, define both directional names and meanings, allowed source/target types, whether symmetric, and an example. Same-type and cross-type connections are allowed; targets stay in this area. Ask only unresolved choices. Completion: the proposed schema and relationship meanings are concrete and reviewable.
5. **Propose.** Follow [schema changes](references/schema-changes.md) in a separate candidate checkout, preserving existing knowledge. Invoke evolve-evaluate with the exact diff, examples and same agent-slug. Open or update one PR/MR using [hosted review](../evolve/references/hosted-review.md). Completion: validated proposal, or explicit remaining failure; human merge activates it.

Return the chosen representation, why it fits, affected types and review URL. No invented relationships to fill a graph. Repository schema extensions remain local to the selected area; installed plugin instructions and other agents' schemas require separate scope.

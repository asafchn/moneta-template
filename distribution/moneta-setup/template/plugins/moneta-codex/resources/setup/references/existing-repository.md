# Existing repository

Use [provider output handling](provider-output.md) and retain wizard answers/verified access. Follow [limited permissions](blocked-write.md) for denied writes.

1. Verify only the supplied destination URL and hosting. Preserve owner, visibility, existing files and memories. Reuse a checkout only after verifying remote and state; otherwise clone the exact knowledge repository into a private local directory.
2. Discover its reviewed base branch and preserve dirty/off-base work separately. An empty remote uses the generated runtime/README base from the new-provider flow. For an existing generated runtime, retain its stable plugin identity, profiles and customizations; unchanged repeated init needs no new review.
3. Propose missing generated runtime files or explicitly requested profile/README changes through review. Use [generation](generate-plugin.md) as the source, preserving conflicting files. A legacy full-source Moneta copy needs a reviewed conversion; keep old files unless their removal is explicitly part of the agreed migration. Never overwrite user customizations with the bootstrap.
4. Initialize only the selected memory area; missing graph/schema files are proposed alongside necessary setup changes. An existing flat/shared graph needs an explicit ownership map before migration. Raise ambiguous ownership and incompatible schemas without deleting old data.
5. Install the verified runtime when available on the approved base. If required runtime/profile changes are pending review, retain preparation and explain the merge step; continue permitted independent work. A different existing target binding requires an explicit switch choice, preserving the old connection until the replacement is ready.

Completion: existing destination resumed without duplication, with exact installation and review states. Organization matching uses the configured URL rule and requires no per-codebase init.
